# PoC: 대표 끝-대-끝 경로 (2026-10-05)

## 질문과 위험

- 가정: 글리프 bank 테이블을 확장 영역으로 옮기고 hi 바이트 4 이상의 새 코드를 쓰면, 원본 문자 핸들러가 수정 없이 한글 글리프를 그린다.
- 위험: (1) hi≥4 경로에서 다른 소비자가 범위를 검사할 가능성, (2) 메시지 재배치(포인터 테이블만 수정) 후 분기·선택지 인덱스 유지,
  (3) 16 MiB 확장 ROM의 적재, (4) 12px 피치에서 Galmuri11 한글의 가독성.
- 통과 기준: 실제 대사 경로(타이틀→Start→Start→A→A)에서 프롤로그 2줄이 의도한 한글로, 의도한 위치에, 그림자 포함 표시되고
  다음 메시지로 정상 진행.

## 입력과 산출물

- 번역 입력: `assets/translation/segments/bank00.json`의 `1fb8a4`, `1fb8e9`, `1fb932` (상태 translated, 개발 정책).
- 빌드: `python tools/build.py --policy development --only-ids 1fb8a4,1fb8e9,1fb932`
  - 산출물 SHA-256 `019a274d326383ab067da29cbfb94fd7e22ad2853387a29bbe6747d0d42ffff4` (16 MiB), 쓰기 5건(원본 영역 15바이트 변경:
    메시지 포인터 3곳 + 리터럴 2곳), 확장 17,423바이트(bank 테이블 + bank4 포인터 테이블 + 글리프 63개 + 메시지 3개).
- 실행: `python tools/emucap_nav.py out/tetsuya-kr.gba work/emucap/poc1 "..."` (Mesen2/emucap, BIOS SHA-1 300c20df…).
  스크린샷 `work/emucap/poc1/prologue3.png`.

## 결과: 통과 (대표 경로 주장에 한함)

- 프롤로그 1·2행이 한글로 표시되고 타자기 효과·메시지 진행이 원본과 같다. 글리프는 흰 획 + 어두운 그림자(픽셀값 1·2).
- 입증한 것: 저장(확장 영역) → bank 테이블 리터럴 2곳 → 글리프 포인터 → 줄 버퍼 합성 → VRAM 경로가 새 코드 공간(hi=4)에서 동작한다.
  메시지 포인터 재작성만으로 재배치가 동작한다.
- 입증하지 않은 것: 분기(0x70~0x73)·선택지(0x72)·{BLK} 동적 타일 토큰이 섞인 메시지의 재배치, 다른 bank의 공유 sub 테이블,
  전체 글리프 예산(최대 3072개 새 코드, 확장 공간 8 MiB), 실기 적재. 글리프 가독성의 최종 판단은 사람 몫이다.
- 관찰된 보완점: 반각 숫자가 12px 셀 왼쪽에 붙어 간격이 벌어진다 → `bdffont.py`에서 폭 12 미만 글리프를 셀 중앙에 배치하도록 수정(재검증 필요).
